## 2. Failing Tests Analysis

### 🔴 CRITICAL: N3 Spec Format Normalization Test Failure

**Test:** `tests/test_event_store.py::TestEventStoreNormalization::test_n3_spec_format_normalized`

**Error:**
```
AssertionError: 'a888e3c6de1f90d1' != 'abcdef123456'
- a888e3c6de1f90d1
+ abcdef123456
```

**Root Cause:**

The test expects the `context_id` to be truncated to 12 characters:
```python
# Test expectation (line 228)
self.assertEqual(stored["context_id"], "abcdef123456")
```

But the implementation in `copilot_core/ingest/event_store.py` (lines 253-257) uses SHA256 hashing:
```python
# Implementation
ctx_hash = hashlib.sha256(ctx_id.encode("utf-8")).hexdigest()
normalized["context_id"] = ctx_hash[:16]  # 16 chars = 64 bits of entropy
```

**Behavior Mismatch:**
- **Expected:** Simple truncation to 12 chars: `"abcdef1234567890"` → `"abcdef123456"`
- **Actual:** SHA256 hash truncated to 16 chars: `"abcdef1234567890"` → `"a888e3c6de1f90d1"`

**Impact:**
- Test failure indicates spec vs. implementation mismatch
- Context ID tracking may not work as expected in downstream systems
- Privacy-first hashing is good, but test spec needs to match implementation

**Fix Options:**

1. **Update test to match implementation** (Recommended if hashing is intentional):
   ```python
   # Test should expect 16-char hash
   self.assertEqual(stored["context_id"], "a888e3c6de1f90d1")
   # Or better: verify hash properties
   self.assertEqual(len(stored["context_id"]), 16)
   self.assertTrue(stored["context_id"].isalnum())
   ```

2. **Update implementation to match test** (If truncation is required for compatibility):
   ```python
   # In event_store.py _normalize()
   normalized["context_id"] = ctx_id[:12] if ctx_id else ""
   ```

3. **Hybrid approach** (Best of both):
   ```python
   # Use hash for privacy, but document the behavior
   ctx_hash = hashlib.sha256(ctx_id.encode("utf-8")).hexdigest()
   normalized["context_id"] = ctx_hash[:16]  # Document: privacy-first hashing
   ```

## 4. Blueprint Registration Conflict Analysis

### Issue: Dual Registration of `openai_compat_bp`

**Files Involved:**
- `copilot_core/app.py` (lines 148-152) — registers WITHOUT guard
- `copilot_core/core_setup.py` (lines 904-907) — registers WITH guard

**Current State:**

```python
# app.py — NO guard
try:
    from copilot_core.api.v1.conversation import openai_compat_bp
    app.register_blueprint(openai_compat_bp)
except Exception:
    logging.getLogger(__name__).exception("Failed to register...")

# core_setup.py — WITH guard
if "openai_compat_bp" not in app.blueprints:
    app.register_blueprint(openai_compat_bp)
```

**Potential Issue:**

If both `create_app()` and `register_blueprints()` are called in the same test session (which happens in `test_phase5_integration.py` fixture `app_with_phase5_apis`), the blueprint would be registered twice — once in `app.py` (no guard) and once in `core_setup.py` (with guard).

**Why Tests Don't Fail:**

The tests skip before hitting this issue because `CORE_SETUP_AVAILABLE` is `False` in the test environment (missing dependencies).

**Recommendation:**

Add guard to `app.py` for consistency:

```python
# app.py — ADD guard
try:
    from copilot_core.api.v1.conversation import openai_compat_bp
    if "openai_compat_bp" not in app.blueprints:
        app.register_blueprint(openai_compat_bp)
except Exception:
    logging.getLogger(__name__).exception("Failed to register...")
```

**Priority:** 🟡 Medium — Not currently causing failures, but defensive coding best practice.
